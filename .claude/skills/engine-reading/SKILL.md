# Read a deck's engine (the reasoning loop, over a computed record)

`data/decks/<slug>/engine.json` is v2 since 2026-11-22 (`docs/research/engine-model.md`): the
engine is a GRAPH of typed events between cards, computed from the cards' own Forge scripts —
nodes, `feeds` / `supplies` / `fills` / `makes` / `ends` edges with their proof state,
components (one per consumed event, priced hypergeometrically), stages by rule, lines as event
shapes with the stacks that stamp them, single points of failure, coverage. Nobody places a
card by hand any more. **What the loop writes is the `reading`**: the engineer's words over
the record — what the engine IS, which lines matter and why, where a rule misplaced a card,
what remains open — and the critic's attack on those words against the graph.

**The record is ◆ and the reading is ★; `validate-engine` holds the first to a fresh build and
the second to its form.** A reading that disagrees with the record does not edit the record: it
says so, in `stage_overrides` with a why, or in `open_questions`.

## Loop (max ENGINE_MAX_ITERATIONS = 3, from config.py)

0. **The record** — free, and it is the brief:

   ```bash
   .venv/bin/manamap pilot engine-graph <slug> --write        # recompute; the reading is copied forward
   .venv/bin/manamap pilot engine-graph <slug>                # read it: stages, components, lines, SPOFs
   .venv/bin/manamap pilot engine-graph <slug> --abilities    # every card's parsed events, with coverage
   .venv/bin/manamap pilot engine-facts <slug>                # the verified pairings and the contained combos
   ```

   Read `coverage` first. A card read by the goldfish's readers or by nothing (`reader`), a
   `partial` card, an `unmapped_forge_names` entry — these are the places the graph can be
   wrong, and the reading's job is to say what the parser could not see. A deck whose declaration
   says `targets_from: engine.json` also had its goldfish targets regenerated by that `--write`;
   say so in the summary, because its next goldfish run will read them.

1. **Cache gate** — the engineer pass is about a fifth of what it cost over the v1 model, and
   the critic about a third, but neither is free:

   ```bash
   .venv/bin/manamap pilot cache-status <slug> --routine deck-engine
   ```

   exit 0 = current, report and **do not spawn**. exit 1 = run it. exit 2 = a required input
   is missing (usually `engine.json` itself — run step 0).

2. **Read**: spawn `deck-engineer` with the slug. It writes
   `.agent-out/deck-engineer.json` — a `reading` block and nothing else. Install it:

   ```bash
   .venv/bin/python -c "
   import json, sys; from manamap.pilot.common import deck_dir
   p = deck_dir('<slug>') / 'engine.json'; doc = json.loads(p.read_text())
   r = json.loads((deck_dir('<slug>') / '.agent-out' / 'deck-engineer.json').read_text())
   r.setdefault('written_for', doc['decklist_sha256']); r['stale'] = r['written_for'] != doc['decklist_sha256']
   r.setdefault('critic', doc['reading'].get('critic') if doc.get('reading') else None)
   doc['reading'] = r; p.write_text(json.dumps(doc, indent=1, ensure_ascii=False) + '\n')"
   ```

3. **Mechanical gate**: `.venv/bin/manamap pilot validate-engine <slug>`. On failure, re-spawn
   the engineer with the errors — do NOT hand-fix, and do not proceed to the critic until form
   passes. The gate also recomputes the record; if THAT differs, the list or the parser moved —
   `engine-graph --write` again and start over.

4. **Attack it**: spawn `engine-critic`. Merge its block into `engine.json` under
   `reading.critic`, setting `iterations`. **Preserve the critic block when you merge a
   revision** — the round-N verdict is the context round N+1 was written against.

5. **Iterate**: verdict `fail` and iterations < 3 → re-spawn the engineer with the findings and
   tell it to **rebut rather than weaken**. A reading that defends a claim against the graph
   with the graph, or withdraws it, is worth more than one softened until nobody objects.

6. **Record**, last, only after the verdict is `pass`:
   `.venv/bin/manamap pilot cache-record <slug> --routine deck-engine`. A `fail` reading is
   still saved — it documents what could not be grounded — but say so plainly, and never
   `cache-record` it.

7. **Dispatch the work queue.** Subagents cannot spawn subagents, so the engineer emits
   `open_questions` and *you* run them:
   - `settled_by: "resolve-stack"` → `/resolve-stack`. The common one: a computed line with no
     stamping stack is exactly a scenario waiting to be written, and the stamp is the fact tier.
   - `settled_by: "goldfish"` → an edit to the deck's `goldfish_targets.json` `components`
     block (a `required` mark, a `routes` entry, an `overrides` entry with a why) — a human
     applies it, then `engine-graph --write` regenerates the targets.
   - `settled_by: "parser"` → a Forge name the registry lacks, or a filter it could not read:
     a `config.ENGINE_EVENTS` row or an `ENGINE_FILTER_PROPERTIES` entry, proven by a test.
   - `settled_by: "research-strategy"` → `/research-strategy`. Price it first.

## What the gate can and cannot see

`validate-engine` rebuilds the computed half and refuses a record that differs; it holds the
reading to its form — `written_for` and `stale`, every named line a computed line or component,
every override a card in the 99 with a why, a critic verdict that is `pass` or `fail`.

**It cannot check that a stack SUPPORTS a line.** A ✓ on a computed line means a checker-passed
scenario holds a connected instance of the shape; it does not mean the scenario shows the flow
happening — two radagast lines once cited a stack that showed the opposite. Reading a stack as
support is the critic's whole job, and it is why this loop does not shortcut to the validator.

## Notes

- **Tier discipline.** The record is ◆, recomputed and compared. A line's stack stamp is ✓. The
  reading is ★, and the page says which list it was written for.
- **A decklist edit stales the reading, never the record** — `--write` recomputes the record and
  marks the reading `stale`; the reading is rewritten by this loop, not deleted.
- **`engine.json` is tracked**; `engine-graph`'s printout and `engine-facts` are views.

**Agent output arrives as a path, not inline JSON.** Read the file, validate it, then merge.
