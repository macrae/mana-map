# ManaMap — Product Requirements

**Owner / sole user:** Sean MacRae
**Status:** Vision spec for full build-out. Prototypes exist for every surface; this document defines the target state.
**Format scope for v1:** Commander (EDH)

---

## 1. What this is

A workbench for building, researching, tuning, and piloting Magic: The Gathering decks — in pursuit of actually winning games.

The governing metaphor is a workshop. You walk in. Your decks are on the bench, sleeved and ready. Tools hang on the wall. You pick up the tool you need for the job in front of you.

- **The bench** is your deck library.
- **ManaMap** is one tool on the wall — an embedding-space explorer for cards.
- **Dossier** and **Pilot's Manual** are the documents clipped to each deck.

Naming note: "ManaMap" is used both for the product as a whole and for the embedding-visualization surface specifically. This document uses **ManaMap** for the surface and **the platform** for the whole. Resolve the naming collision before public docs.

### User of one

This is built for one person. There is no multi-tenancy, no auth, no onboarding, no growth surface. It may be open-sourced so others can run it, but no requirement in this document is motivated by a second user. When a tradeoff appears between generality and Sean's workflow, take the workflow.

| Not building | Why |

## 3. Deck model

### 3.1 States

| State | Meaning |
|---|---|
| **Pinned** | 1:1 with a physical sleeved deck. This is a real object that exists. |
| **Workbench** | Brewing. Digital only. Not yet sleeved. |
| **Deprecated** | Tried, evaluated, retired. Kept for the record, out of the main view. |

Pinned decks are the center of gravity for analytics, research, and optimization. Workbench decks are the center of gravity for exploration and construction.

### 3.2 Versioning

Semantic versioning, one immutable pin (hash) per iteration.

| Bump | Trigger |
|---|---|
| Major | Overhaul — swapping out a set of cards, changing the deck's plan |
| Minor | Engine change — adding/removing a synergy package |
| Patch | Mana base, single-card swaps, tuning |

**Requirement:** every artifact derived from a deck (Dossier, Pilot's Manual, simulation run, benchmark score) is stamped with the deck pin it was generated against, and the UI shows when an artifact is stale relative to the current version.

*The exact bump rules above are a proposal — confirm before implementing.*

## 4. Surfaces

### 4.1 Workbench — landing page

Highly visual deck library. Answers one question on open: **what am I playing tonight?**

Requirements:
- Pinned decks lead. Workbench decks below. Deprecated collapsed or on a separate view.
- Each pinned deck card surfaces its headline simulation metrics and its aggregate benchmark score.
- One click into a deck detail view; from there, one click to Dossier, Pilot's Manual, simulation history, and version log.
- Aggregate stats across the whole library (card pool coverage, color distribution, how many decks are stale).

### 4.2 ManaMap — embedding-space explorer

Sub-pages:

| Page | Behavior |
|---|---|
| **Discover** | Opens on a random card, or a card you name. Explore outward from there — nearest neighbors, click to re-center, walk paths. |
| **Explorer** | Zoomed out. All ~30k cards in space with subtle motion. Overlays/skins toggle the coloring: mana color, card type, subtype. |
| **Deck view** | Any deck rendered in the space. Combo lines drawn as directed graphs with explanatory text on the interaction. *(Built.)* |

The graph structure underneath (nearest neighbors, random walk, path construction) already exists and should be reused rather than rebuilt.

**Aesthetic decision required before UI work starts.** Current skin reads as 1998 — the uncanny middle. Pick one and commit:

- **2030** — clean, high-end, futuristic, space-like. Depth, restraint, real typography.
- **1980** — pixelated, retro, unapologetic.

Half-measures land back in 1998. This is a blocking decision, not a polish item.

### 4.3 Dossier — the case file

One to two pages. What a PI hands you on a subject. Quick-flip, no reading required.

Contents: what the deck is designed to do, current rank against the library, how long it has been in development, version and pin, headline simulation stats, current status.

### 4.4 Pilot's Manual — the playbook

How the deck actually works: engines, how the pieces fit, combo lines, what to mulligan, what to tutor for, sequencing. Visual and skimmable, but it has real content and rewards attention.

**Rewrite required.** Current output is too dense and too academic.

| Cut | Keep |
|---|---|
| Commander 101 — command zone, tax, color identity | Mechanics that actually matter to piloting *this* deck (e.g. a stack-resolution subtlety a line depends on) |
| Rules citations | Named lines, with the trigger and the payoff |
| Exposition paragraphs | Tips, gotchas, "watch for this" |
| Wall-of-text density | White space. Air. |

Standard: respect the reader's time. He knows the format. Tell him what he'd forget.

## 5. Agent layer

The agent is **another sub-agent in the existing pi harness**, not a parallel system. Jarvis in the workshop: you're at the bench, you ask it for something, it goes and does it.

### 5.1 Tasks

| Task | Description |
|---|---|
| Build a deck | Seed → finished list (§7) |
| Research a deck | How is this commander/archetype built in the wild, what's it trying to do |
| Take feedback | "This deck stalls on turn 5" → analysis and candidate fixes |
| Optimization scan | Read a deck, surface improvement candidates |
| Pattern analysis | Across the library — what am I over/under-playing, what do my decks have in common |
| **Obsolescence scan** | Sweep decks for cards superseded by newer printings: strictly better, cheaper for the same effect, or close enough. Must state the case for keeping the incumbent, not just the swap. |

### 5.2 Deployment constraint

The deployed site is static (GitHub Pages) and cannot make LLM service calls. The platform therefore has two modes:

| Mode | Capability |
|---|---|
| **Deployed / static** | Browse, explore, read Dossiers and Pilot's Manuals, view decks in embedding space. Read-only. |
| **Local** | Everything above, plus the full agent layer, simulation, and brew flow. |

**Requirement:** when running locally, the agent is embedded *in the UI* — not a separate terminal the user context-switches to. Closing the gap between the front end and the agent back end is the single largest UX requirement in this document.

The static build must degrade gracefully and visibly: agent-dependent affordances are absent, not broken.

## 6. Commander search

Given a set of cards, find the commanders worth building toward. Designed so archetypes **emerge from real decks** rather than being pre-labeled.

### 6.1 Algorithm

1. **Seed.** User supplies ~20 cards (from a collection, a basket, or hand-picked).
2. **Seed embedding.** Compute an average embedding over the seed. Exclude basic/generic lands; retain specialty and utility lands, which carry real signal.
3. **Color filter.** Filter the legendary pool to the seed's color identity. Crude first cut, cheap, effective.
4. **Reference pull.** Fetch the top ~20–25 commanders for that color identity from EDHRec, on the fly — rankings move, so don't freeze them.
5. **Reference centroids.** For each commander, pull a representative decklist and compute its centroid under **the same exclusions and controls** as the seed.
6. **Type control — critical.** A seed that is all instants and sorceries will embed nowhere near a full deck's centroid, because the reference deck is mostly creatures. Compare like against like: restrict the reference centroid to the card-type composition of the seed, or weight by it. Without this, the ranking measures deck composition rather than deck identity.
7. **Rank** commanders by proximity of centroid to seed.
8. **Render** as a scatter. Hover to inspect a commander deck; click to open it.
9. **Open the reference deck in ManaMap** — full embedding-space view, graph structure computed on the fly.
10. **Harvest.** Select cards out of that deck into the basket. Continue to the brew flow (§7).

### 6.2 Direct entry

The user often already knows the commander. "I want to build Zur." Skip to step 9 with that commander's reference decks — same downstream flow.

### 6.3 Known weakness

The embedding is built on Oracle text, and text is fuzzy. Cards with similar phrasing can do meaningfully different things and still sit close together. Commander search inherits that error.

Two consequences:
- Treat proximity as a discovery aid, not a verdict. The UI should invite inspection, not assert a match.
- Every improvement to the embedding improves commander search, deck view, obsolescence scan, and pattern analysis simultaneously. It is the highest-leverage back-end investment in the platform.

See spike S1.

## 7. Brew flow

The path from "I have some cards" to "there is a versioned deck on my bench."

```
collection / explorer / reference deck
            │
            ▼
        [ basket ]  ← persistent, cross-surface
            │
            ▼
   archetype selection (agent research)
            │
            ▼
   role template — engines to fill
            │
            ▼
   candidate surfacing (embedding space)
            │
            ▼
   agentic build-out — mana, gaps, curve
            │
            ▼
   new deck @ v0.1.0 on the Workbench
            │
            ▼
      simulate → log → iterate
```

### 7.1 Basket

A persistent object the user fills from anywhere — Explorer, Discover, a collection, an EDHRec reference deck. Survives navigation between surfaces. This is the connective tissue for the whole flow and should be built first.

### 7.2 Archetype selection

The agent researches how the chosen commander is actually built and presents the distinct styles. Zur, for example, splits into a Voltron enchantment build that suits up and kills fast, and a stax/combo build that grinds. Both are legitimate.

**Requirement:** present styles side by side without ranking them. Win rates and play rates may be shown as data. The platform does not tell the user which deck to want.

### 7.3 Role template

Once a style is chosen, the agent produces the role list that style needs — fodder, life gain, removal, ramp, draw, protection, whatever fits. For each role, it surfaces candidates from the embedding space filtered to color, type, and (optionally) owned collections.

The user clicks through and selects. The agent proposes; the user builds.

### 7.4 Build-out

The basket (typically 15–25 cards) goes to the agent, which completes the deck: mana base optimization, gap filling against the role template, curve. Opinionated enough to produce a functional list, not opinionated about strategy.

Output is a new Workbench deck at v0.1.0, ready to simulate.

## 8. Collections and inbox

Bridges paper to platform.

- Bulk cards get scanned and land in an **inbox** for triage.
- Triaged cards are grouped into a named **collection** ("2026 bulk haul").
- Collections are reusable and composable — a brew can be scoped to one or several, constraining the build to cards actually owned.
- When the build wants a card outside the collections, it is surfaced as an acquisition: what to buy, and why it's worth it.

Ingestion method is unresolved — see spike S4.

## 9. Benchmarking and simulation

### 9.1 Metrics

Simulation produces per-deck measures. Named so far:

| Metric | Reads on |
|---|---|
| Mana screw | Frequency and severity of mana failure |
| Speed | How fast the deck executes its plan |
| Consistency | Variance across games — does it do its thing reliably |
| Response | Ability to answer what the table does |

These roll up into a **single aggregate benchmark score** that makes decks comparable to one another.

### 9.2 Controlled experiments

The aggregate is only meaningful if the simulations are controlled. Same pod composition, same seeds, same game count, same conditions across decks. Uncontrolled sim output cannot be aggregated into a ranking.

**Requirement:** define the standard benchmark harness — pod definition, iteration count, seeding, and metric extraction — before publishing scores to the Workbench.

### 9.3 The payoff

Tuesday night. Open the Workbench. The library is ranked. You know which deck is your most tuned build and you sleeve it. That is the feature.

The aggregation formula is an open decision (§12).

## 12. Sequencing

### Phase 0 — Decisions (blocking)
Aesthetic direction. Semver bump rules. Benchmark aggregation formula. Naming collision.

### Phase 1 — Foundations
Deck data model, versioning, pins. Persistent basket. Deck detail view. Navigation shell across the four surfaces.

*Everything else depends on this phase. Nothing should start ahead of it.*

### Phase 2 — Commander search
EDHRec ingestion. Centroid computation with type control. Scatter UI. Reference-deck rendering. Harvest to basket.

*Gated on spike S1 — if the embedding doesn't discriminate, this design needs revisiting before build.*

### Phase 3 — Brew flow
Archetype selection. Role templates. Candidate surfacing. Agentic build-out. Output to Workbench as a versioned deck.

### Phase 4 — Benchmarking
Controlled harness. Metric extraction. Aggregate score. Ranked library on the Workbench.

*Independent of Phases 2–3; can run in parallel with a separate owner.*

Gated on S4. Parallel track — brew flow works without it, just without the "only cards I own" constraint.

Pilot's Manual rewrite. Aesthetic implementation. Dossier layout.

*Can start any time after Phase 0. Not on the critical path.*

## 13. Format support

v1 is Commander. Design the constraints as **parameters**, not assumptions — retrofitting format-awareness after the fact is expensive.

Formats to accommodate, per Scryfall's legality data:

| Format | Shape |
|---|---|
| Commander | 100, singleton, legendary commander, color identity |
| Standard / Modern / Pioneer | 60, format-legal pool |
| Pauper | 60, commons only |
| Penny Dreadful | 60, budget-constrained pool |
| "Pendragon" | Described as pauper commander with a single legendary artifact — *name and rules unverified, confirm before scoping* |

The parameters that vary: deck size, singleton rule, commander requirement and type, legal card pool, color-identity enforcement. Commander search, brew flow, role templates, and benchmarking all read from the same format config.

## 14. Open questions

1. Benchmark aggregation — how do mana screw, speed, consistency, and response combine into one number? Weighted sum, or something that penalizes a floor?
2. Semver bump rules — confirm the major/minor/patch mapping in §3.2.
3. Reference decklists — one representative list per commander, or an average across many? Averaging is more robust and less interpretable.
4. Collection storage model — how do collections version as cards move in and out of physical decks?
5. Agent invocation surface — command palette, chat panel, or contextual actions attached to objects?
6. Does a pinned deck's physical state need reconciliation? If a card is pulled from a sleeved deck for another build, does the platform know?
7. Aesthetic: 2030 or 1980?
