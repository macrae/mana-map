# The card map

Everything measured about `viz/` — the canvas renderer, the force graph, the three modes, the library and its piles, the shell. Read before touching anything under `viz/`.

Extracted verbatim from `CLAUDE.md` — every measurement here was in that file and none was reworded. `CLAUDE.md` loads into every session; this does not, so the rules that bite regardless of what you are touching stayed there and the full record moved here.

- **Viz serving root**: all fetches are `../data/<file>` relative to `viz/index.html` — `viz/` and `data/` must stay top-level siblings; serve from repo root.
- **Cache busting**: bump `?v=N` on the script/CSS tags in `viz/index.html` **and `viz/deck.html`** after any JS/CSS change. `index.html`'s **nine** script busts must move together — a test asserts it, since a mismatched pair is how `build.js` ends up calling a stale `mana-map.js`. `manuals/magazine.css` is content-addressed instead (`?v=<sha8>`), so a CSS edit there obligates rebuilding every manual page.
- **Synergy ≠ Similar**: synergy is complementary (blink→ETB, rule-based); Find Similar is embedding neighbors. Different algorithms.
- **One renderer: `viz/js/render/canvas.js`.** Plotly is deleted — no CDN tag, no `?renderer=` flag. `render()` builds a layer list and hands it to `setLayers`; `updateLayerBy(flag, patch)` is the restyle fast path (drill's 90 frames, the browse marker) and matches on a flag like `_isDrill` rather than a trace index. `mapRenderer.layers` is the read side (what `gd.data` was) and `getCamera`/`setCamera` speak **data units**, so span-keyed logic needed no change. **A renderer kept behind a flag is a renderer nobody is testing** — three bugs lived in the canvas path for as long as it was opt-in, each invisible because the default path never executed it.
- **Data cache-busting**: `MM.DATA` URLs carry `?v=DATA_VERSION`. Bump it whenever a consumer would draw a **different conclusion** from the bytes — not only when the parser would. Schema changes (new key, renamed field) obviously qualify; so does a retrain, which keeps every shape identical and changes every value. Caught in a browser after the embedding rebuild: the page happily served the pre-retrain neighbours for Doubling Season out of cache while a cache-busted fetch of the same URL returned the new ones. A pure content *refresh* (same model, new Scryfall dump) still does not need it. Adding `membership` to `regions_*.json` broke drill-by-region for every browser that had already cached the old shape — politely, which is what made it expensive to find.
- **A global pixel aggregate cannot distinguish two changes that cancel.** `test_the_spotlight_actually_dims_the_canvas` counted green over the WHOLE canvas, and clearing a spotlight does two things at once: it rests the line you were looking at and it un-mutes every other verified line. On goblin-storm those cancel — 868 green px spotlit against 833 cleared (0.96, squarely in the range reserved for the bug) while the line's own box goes 1024 → 301, and the bounding box goes from 47×294 to 591×687. The test reads `Force.spotlitRows` and measures near those cards now. Its threshold is measured on BOTH sides — healthy 0.204–0.439, resting-ink-disabled 0.589–0.695, so 0.52 sits between — because a threshold chosen only from passing runs says nothing about what it catches.
- **A call that returns early and silently is the worst kind of race, because nothing is slow.** `mapRenderer.setCamera` no-ops while `baseFit` is null (it is built on the first `setLayers`), so a test that moved the camera too early simply did not move it and then measured the FITTED view — `test_canvas_draws_density_contours` read a halo-saturated 38.7 ink instead of 3.8 and called it "contours stopped drawing", one full-suite run in three, while being byte-identical five times in isolation. Fixed in `canvas_page`, NOT in the test: the fixture waited for the canvas element and the data but not the fit, so every test on it had the hole. The probe is the renderer's own — `getCamera()` returns null under exactly the condition that makes `setCamera` a no-op. **Do not retry inside the poll**: putting the `setCamera` call in the `wait_for_function` predicate made it worse (3 runs in 6), since re-applying the zoom transform every frame leaves the camera back at the fit.
- **The browser suite parallelises (`-n 4`, 232s against ~600s) and doing it found five latent flakes.** No fixture surgery was needed — `viz_server` already picks a free port per session and `browser` is session-scoped, so xdist gives each worker its own. Every one of the five was a fixed `wait_for_timeout` measuring the machine instead of the behaviour: two read a stale status string, one a camera mid-transition, one an `src` our own code had not written yet, and one the fitted view. **The `canvas_page` `getCamera()` readiness wait is necessary but NOT sufficient** — selecting the map starts a render ending in a fit, which under load lands *after* the test's camera move and silently undoes it; the fix is a bounded retry with a settle between attempts, which is not the thing that failed before (`setCamera` inside a `wait_for_function` predicate re-applies the zoom every frame and pins the camera at the fit). One test is `serial_only`: `test_canvas_render_beats_the_plotly_budget` asserts 30ms and measured 41ms sharing a machine with three Chromiums — **a performance assertion under contention measures the contention**.
- **Frontend source-assertion tests catch nothing**: `test_viz_{drill,deck_lens,viewer}.py` grep JS as text. A `ReferenceError` that killed drill mode outright passed all 13 drill tests. Real coverage lives in `tests/test_viz_behaviour.py` (playwright, `-m browser`) — add there when you change rendering or interaction. See `docs/testing.md`.
- **Explore grows in place, and which relations get an arc is MEASURED.** Clicking a relation in Explore adds to the graph and draws the edges at the cards' true atlas positions — it no longer switches modes (that was the second of three designs; the first was a browse-set fork). `MAP_ARC_RELATIONS` encodes median edge length vs a random pair on the same map: default map draws **similar** (0.60×) and **outclassed-by** (0.29×); the ability map draws **neither** (0.27u apart on a 71u map — an arc is one pixel, so drill is offered instead); **synergy is never drawn on either** (0.95× / 1.04× = noise), because it is *complementary* and its partners belong in different regions by construction. Its partners still join the graph and the status points at the force layout. Drawing all three would look richer and render the most interesting relation as spaghetti.
- **THE SEARCH BOX ASKS TWO DIFFERENT QUESTIONS, and in Discover it was asking neither.** Typing set `searchTerm` and called the MAP's `render()` — but Discover hides the atlas canvas, so the white diamonds landed on a surface nobody could see and the only observable effect was a status line. **There was nothing to click.** In Discover it is a PICKER now: names ranked out of `Discovery.index` client-side, so it works on the deployed site (Build's commander picker calls `Api`, which Pages lacks) and **before the 12.9 MB projection lands**, which is the entire point of booting on 0.56 MB. Ranking is `serve.py:_commanders`' rule ported — normalise punctuation, exact, then starts-with, then shortest. **Two controls, never one**: the name REPLACES the walk, `+` ADOPTS, and `+` appears only once `Force.nodeCount > 0` — the same rule the seed textarea keeps, because a single control that switched silently destroyed walks twice. In Explore it FILTERS: matches lit, everything else receded to 0.09, camera framed on the matches, **and Escape puts the camera back** — a framing with no way home leaves the pilot zoomed into a corner with the whole atlas shown again and no idea why.
- **THE LEGEND HAD NEVER BEEN CLICKABLE WITH A MOUSE, and every test passed.** `.map-legend` carries `pointer-events: none` so it does not eat drags over the canvas beneath it, and nothing re-enabled it on `.map-legend-row` — so clicks never reached the handler while `cursor: pointer` showed a hand over an inert element, under a comment reading "The legend is a control, not a caption". It survived because every legend test dispatches **`row.click()` in JavaScript, which bypasses hit-testing entirely**. The fix is one line, and the correct pattern was two rules above it (`.map-labels` sets `none` on the container and `auto` on the child). **A test that synthesises the event cannot see whether the element is reachable** — assert `document.elementFromPoint` at the row's own centre, or use the driver's real click.
- **THE LEGEND IS A MULTI-SELECT FILTER: `legendKeys` is a Set, empty means everything.** Still GROUP KEYS and never a row set — the original single-key comment's argument survives intact, because a Set of keys is still one comparison per group and never touches the 34,890-entry opacity array. It joins `spotlightFor` beside `regionFocus` and `queryFocus`, and — this is what makes it a FILTER rather than a spotlight — it joins **`narrowedTo`**, so the status count, the Drill button and `MM.passesFilters` stay one answer. Non-selected groups RECEDE rather than vanish, same as the search filter and for the region-focus reason. **Two controls over one axis is safe here for a structural reason, not luck: the legend is built from the TRACE LIST, so it can only ever list groups that survived `activeSupertypes` — a hidden group has no row to click**, so the toolbar buttons and the legend cannot contradict each other. Do NOT write `activeSupertypes` from the legend: their default polarities are opposite (all-on vs none-selected) and their drawing semantics differ (hide vs dim). `MM.focusGroup` keeps REPLACE semantics so Build's role bars are untouched, and `MM.legendFocus` still returns `{key}` for the first selection so nothing downstream had to move. **A selection does not survive its key space** — the `#colorBy` handler clears it, because "Red" means nothing under rarity and as a filter it would select zero cards rather than merely lighting none.
- **A FILTER IS A SET, AND A SET IS BROWSABLE — the walk is a THIRD ORDERING, not a new mode.** `browseSet` was already an ordered array plus a cursor, arrows already drove it through `cycleSelection`, and `renderBrowsePanel` already painted the identical card body as a click. So stepping through a filtered set is `orderByNearestWalk(rows)` sitting beside `orderByCentroidDistance` — greedy: start at the card nearest the set's centroid, then always take the nearest unvisited. Measured on the treasure filter: **consecutive cosine 0.954 against 0.855 for a random pair from the same set**. **The tour is MATERIALISED UP FRONT AND CAPPED (`WALK_MAX = 1000`)** because it is O(n²·d) — 24M multiply-adds at 433 cards, **2,960M at 4,809** — while a lazy per-step walk is ~55k but leaves `preloadNeighbourImages` nothing to warm, and image latency is "most of what made the old panel feel slow to browse". Above the cap the centroid order stands **and the panel says so**: the label was a two-way branch and its own comment calls it "the only thing making this browsable", so a third ordering without a third branch has the panel stating a sequence the cards are not in. `browseHighlightKey` gained an order tag — it hashed `length:first:last:anchor:space`, so two orderings of one set with the same endpoints hashed identically and skipped a rebuild that really had moved every point.
- **`getCamera().y` COMES BACK DESCENDING, and comparing against it unordered silently inverts a test.** Screen y grows downward, so a fitted view reports something like `[8.2, -40.1]`. The browse camera's "is this card already on screen" check compared `p[1] > cam.y[0]` against unnormalised bounds, so **every point failed and it panned on every step** — the always-re-centre behaviour, arrived at by accident and indistinguishable from a design choice. Normalise with min/max before comparing, and **preserve the camera's own orientation when writing back** or the map flips vertically on the first pan. Caught only because the test asserted the opposite property ("the camera did NOT move on a step whose card was visible").
- **A FILTER UNIONS; A CASCADE FINDS. Measured, and the first version got it backwards.** The old search stopped at the first tier that matched anything, which is right for finding a card and wrong for narrowing an atlas: **"treasure" returned ONE card**, because a card is named exactly "Treasure" and the exact tier fires first — while **390 carry the treasure KEYWORD and 413 mention it in oracle text, union 433**. An "exact name is unambiguous intent" shortcut was then tried and also removed: it reproduced the same bug, and it bought nothing, since a full card name unions to 1 (`Craterhoof Behemoth`, `Counterspell`) or 3 (`Sol Ring`). One rule, no special case. The status names the **two biggest contributing fields with their counts** — they OVERLAP so they are listed rather than summed, and 433 on its own cannot tell a reader which question was answered. Keywords (`d.k`) are searched for the first time; oracle/type/keyword all need the projection, so an empty `allData` reports **"loading"** rather than an empty result that reads as "none".
- **DRAWN ≠ NARROWED, and naming them apart is the fix.** Three copies of the filter predicate exist and the documented bug is them disagreeing by accident. `visible` in `render()` stays supertypes-only, so a search RECEDES non-matches instead of hiding them — the precedent the region focus already set ("clicking a region left you staring at a cluster with no idea where it sat"). `narrowedTo(d, i)` is the other question — what the pilot singled out — and it is what `Drill ⤓` re-maps and counts, so `MM.passesFilters` takes a ROW INDEX now: a search narrows by row, not by any property of the record. The query joins `spotlightFor` as a second row Set beside `regionFocus`, never as a second dimming path.
- **Role colouring is Build's language, and it leaves Explore's picker WITHOUT leaving the registry.** `MM.GROUPINGS.role` must stay: `build.js` reads its `order` and `palette` through `familyPriority()`/`familyColour()` at six call sites. And the `<option>` cannot simply be deleted either — clicking a Build role bar calls `MM.focusGroup(key, 'role')`, which does `select.value = 'role'`; with no such option that assignment **silently no-ops** and the select then disagrees with `currentColorBy`, which is the exact failure its own comment warns about. So `MODE_GROUPINGS` hides it per mode and falls back to `supertype` if it was selected on the way in. It must be synced at BOOT as well as in `setMode`, because only Discover gets its chrome applied before the data lands — arriving on `?mode=explore` otherwise shows an option that mode does not offer.
- **Three modes: Discover, Explore, Build.** The Walk was Discover with different chrome (four `chrome ===` reads = two behaviours + a status string) and is deleted — its panel's keepers (scoreboard, Fit, Reheat, Start over, trail, truncation notice, **region seeding**) moved into `Discovery.render`. Deck Lens + Build Deck merged into `viz/js/build.js` / `window.Build`. **`?deck=<slug>` now lands in Build** — it is an inbound contract from the dossier and every published manual, so it must keep working.
- **Deleting a mode can make a capability unreachable without deleting it.** `Force.seedFrom` (box-select → graph) was reachable only by entering The Walk with a selection live. Removing that mode left the function working and callerless — the quietest kind of regression, since nothing fails. `MM.growFromBrowse` is the caller now. When you delete an entry point, grep for what only it could reach.
- **The exported brief IS `brief.json`.** `Discovery.brief()` emits the exact shape `pilot/build_deck.py:load_brief` reads — `{slug, commander, bracket, must_include, must_exclude}` — so it can be saved to `data/decks/<slug>/brief.json` and run. Round-trip verified: `load_brief` accepts it, tolerates the `_manamap`/`next_step` extras, and its derived identity matches. Two rules taken from the Python side rather than guessed: **colour identity is DERIVED from the commander, never authored** (it rides in `_manamap` as information), and **budget is unsupported** because prices are stripped. `must_include` is the TRAY, not the pool — and it warns when ≥89 of 99 slots are pinned, which is what loading a whole deck does.
- **`Session.setCommander` must be written wherever a commander is learned.** `importText`, `loadDeck` and `Build.seedGraph` all set the graph's ring via `opts.deck`; only Session is read by the brief. Writing one and not the other produced `commander: null` for a deck whose decklist named its own commander with `*CMDR*` — which `build-deck` refuses outright.
- **The panel belongs to the MODE, not the engine.** One force engine, two owners. Deleting The Walk collapsed `Force.renderPanel` to "Discovery always owns the panel" — true with one graph consumer, false the moment Build seeded the same engine, and every reheat then repainted Build's roles and curve with Discover's landing controls. `renderPanel` asks `MM.mode`. Three call sites had the same assumption: `renderPanel`, `Force.pinCard`/`branchFrom`, and `MM.relate`, all reaching for `Discovery.focus`, **which renders**. Use `Discovery.setCurrent(row)` to note the open card without claiming the panel.
- **Build owns its graph; a walk you grew is yours.** Leaving Build calls `Force.newWalk(true)` so Discover gets a clean landing card — otherwise it opened on someone else's 97-card deck. **Explore is exempt**: it is a lens on whatever graph is current, so clearing on the way there would empty the thing it exists to show. `currentMode` is assigned before the `exit()` calls in `setMode`, which is what lets `Build.exit` tell those two destinations apart.
- **`viz/js/build.js` owns Build mode: a lens, not a scorer.** It reads `card_roles.json` in the browser and renders the role histogram, Short List, verified lines and copies-vs-dots, plus colour identity, format legality, the curve and the colour load. The role taxonomy lives in `MM.GROUPINGS.role`, reached through `familyPriority()`/`familyColour()` — never redefined here, because two taxonomies on one screen is two legends that can never agree. It deliberately does **not** score cards: evaluation comes from the pipeline via the exported brief, so there is exactly one scorer. **Two dimming paths live in one module**: `dimsAll()` (one scalar, ~free, the normal case) stands down via `!showIllegal` so `getDimmedIndices()` can single out what you cannot legally play — if both were true the scalar would win and nothing would be singled out.
- **The deck-builder's six-factor scorer is deleted, deliberately.** Measured against `config.DECK_BUILD_WEIGHTS`: two of six factors had no counterpart (JS keyword-Jaccard vs Python castability), three of four shared weights differed, and two shared factors used different curves — Python's `synergy_affinity` docstring says the synergy graph "is a retrieval aid and not a scoring function", which is exactly what the JS used it as. It cost ~50 MB of lazy downloads to be wrong differently from the pipeline. Suggestions come from the precomputed relations; **evaluation comes from the sub-agent routine via the exported brief**. Cards you add go to the **library** (Session), not a ninth set-of-cards container.
- **`localStorage['manamap-deck']` is gone and should not come back in that form.** It stored raw positional row indices with no schema version, so a Scryfall refresh that reorders `cards.csv` silently reinterpreted a saved deck as different cards; restore did no range check, so entering Build before the projection landed threw.
- **The LIBRARY is persisted, and it stores NAMES.** `Session.tray` was renamed `Session.library` and now survives navigation and reload (PRD §7.1 — "the connective tissue for the whole flow"). Vocabulary first: in Magic your library IS your deck, so the cards you gather while brewing are the deck you are gathering; **the bench** is every deck you own, and the two words must not swap. The storage rules come straight from the bug above: card **names** never row indices, a **schema version** (`v: 1`), a corpus **fingerprint** that is informational rather than invalidating (names are stable, so a refresh explains a shortfall instead of causing one), a **range check** on every restore, and an unknown schema is **left on disk and ignored** so a newer build's data survives an older build reading it. A name that no longer resolves is REPORTED — a library that quietly comes back two cards short is indistinguishable from one that came back whole. The name resolver is **injected** (`Session.useCards`, the same shape as `useGraph`) because `session.js` loads before `mana-map.js` and touching `MM.*` at its top level is the boot-order failure that once broke four files from one mistake; Discovery registers it when `viz_index.json` lands, which is the first moment a name can become a row. `test_the_library_stores_names_not_row_indices` reads the stored BYTES rather than the behaviour, because the behaviour only diverges after a corpus refresh and by then it is too late — proven by re-introducing the bug, which stores `[14493]` where `["Sol Ring"]` belongs.
- **THE LIBRARY IS A LIST OF NAMES; A ROW IS A RESOLUTION OF A NAME — and it is a PLACE, not a number.** It had no content view anywhere in `viz/`: you could add to it, you were told how many things were in it, and the only way to see WHAT was to export a JSON file. There was no per-card remove — the one removal control was an unconfirmed **Clear** inside a collapsed `<details>` labelled "Start somewhere else", a destructive control mislabelled by its container. **FOUR COUNTERS READ THREE REPRESENTATIONS**: the strip took `localStorage.cards.length` (raw names), Discover and Build took `Session.library.size` (resolved, deduped ROWS), and a draft status took `brief.must_include.length` — with nothing reconciling them, because memory held rows and disk held names and `nameOf`/`rowOf` **are not inverses** (`rowOf` returns the FIRST row of a name, and 38 of 34,890 names sit on more than one row). Entries are `{name, row}` with `row` possibly -1, which settles four defects at once: **`save()` needs no corpus**, so the two surfaces that never load one can take a card back OUT rather than only count it; **an unresolvable name is KEPT** and drawn as a tile that says so, instead of being dropped from memory, left in the store and counted forever by a strip no surface could satisfy; **dedupe is by name**; and **`useCards` writes once** when the restore changed anything, because a read-only restore left the disagreement permanent across every reload of every page. **Loading happens at module init, NOT in `useCards`** — the first cut restored inside it, which only the Atlas calls, so the workbench drawer opened empty beside a strip counting eleven cards out of the same store: the identical bug, one surface over. **`add`/`remove` exist because `toggle` in a loop is a bug** — `resumeDraft` restored a brief by flipping each must-include, so a repeated name cancelled itself out while the status quoted what it MEANT to keep. **THE REPAINT IS A SUBSCRIPTION**: `MM.keep` repainted only in explore and build, so in discover it wrote to Session and told nobody — measured, no reload involved, strip `empty→1→2` against a tray frozen at `2`, which is the whole of "it says two cards, only shows one". Adding `discover` to that list would have left the fourth panel to rediscover it; every panel that draws library state now listens, and **forgetting Explore's was the first cost of the change** (the Keep button read "+ Keep this card" over a card already held). Art comes from `Shell.cardImageUrl` at `version=small` — a NAME is the only card identity the browser ever has, which is also what lets a page with no corpus draw real cards — lazy, with the box reserved at `488/680`, and a DFC's `A // B` retried on its front face. Opening a tile routes through **`MM.openCard`**, never `Discovery.show`: that calls `newWalk(true)`, so opening a card you kept would silently delete the walk you kept it from. A `storage` listener keeps a second tab honest.
- **THE LIBRARY HAS PILES — one card, one zone — and the schema went to v2 by UPGRADING rather than ignoring.** `{v:2, corpus, active, zones:[{name, cards:[names]}]}`. A card is in exactly one pile, which is the physical metaphor the library already runs on (the cards you are gathering) and what keeps every count unambiguous and `remove` meaning one thing; considering a card for two decks means picking one, which is what `move` is for. **The v1 upgrade is the load-bearing part**: the "unknown schema is left on disk and ignored" rule protects a NEWER save from an OLDER build, and this is the other direction — the data is ours, readable, and refusing it would silently empty a real library. v1's `cards[]` becomes one pile named `Unsorted` (not "Library": the whole thing is the library, and a pile named after its container says nothing about its contents — it also states the honest thing, that those cards were never sorted because there was nowhere to sort them to). Dedupe is across the WHOLE library, not per pile. **Scope is the design question everywhere downstream**: `names`/`size` are the whole library and are what the strip counts; **`zoneNames` is the ACTIVE pile and is what a brief and a draft export**, because a brief is one deck and exporting every pile would put an artifact collection into a Zur build. A kept card lands in the pile you are LOOKING at — anything else means sorting every card twice. **Deleting a pile MOVES its cards** and the confirmation says where they go, because deleting a label is a statement about the label; the last pile cannot be deleted, since a library with no pile has nowhere to put the next card. `clear()` is the whole library and `clearZone()` the open one — the drawer's button is the second and names the pile in its question.
- **TWO BUGS THE PILES SHIPPED WITH, and both are the same shape: a reader that predates the schema and keeps answering.** (1) `Shell.libraryNames`' localStorage FALLBACK was written against v1's flat `cards` and not revisited, so a v2 document read as **empty** — the strip saying "library empty" over a full library, in exactly the window before Session boots where that branch is the only reader there is. **A fallback that silently answers zero is worse than no fallback, because zero is a plausible answer.** It reads both shapes now, and its test hides `window.Session` to force the branch, which is the only way to reach it on a page that loads Session. (2) Dedupe is library-wide, so `add` on a card already held was a no-op — correct for "keep this", **wrong for "put it HERE"**. `resumeDraft` clears the open pile and re-adds the brief's must-includes, so one already sitting in a DIFFERENT pile was deduped away: the draft came back short, the status quoted the brief's count rather than what landed, and the deck's own card stayed filed elsewhere. Measured: a two-card brief gathered one. **An explicit zone now MOVES; a bare `add` still no-ops**, because "keep this" said of a card already kept is not a request to relocate it — and both halves are asserted, since a fix that moved on every add would silently drag cards out of the pile they were sorted into.
- **One shell, three surfaces, and the vocabulary is fixed there** (`viz/js/shell.js`). **THE WORKBENCH is the landing page and the thing all of this IS** — the surface the tools sit on, not one tool among them. **THE ATLAS is a tool on the workbench**: 34,890 cards in embedding space (`index.html`). **YOUR LIBRARY** is the cards you are gathering. That resolves the naming collision the PRD flags in §4.2 — the product is the Workbench, the embedding surface is the Atlas, Mana Map is the wordmark over both. Before it, three pages had three headers linking to different subsets of each other, and `workbench.html` — which IS the workbench — linked to the atlas under the name "the bench". The strip has **zero dependencies**: it reads no `MM`, no `Session`, no artifact, which is what lets it live on two pages that load neither. **The library COUNT comes straight out of `localStorage`, and it is legible there only because the library stores names** — a count of names needs no corpus, so a page that has never heard of a card can show it; row indices would have forced the whole index onto both pages, which is the quieter second argument for the names decision. **`save()` must run before `emit()`**: the shell reads the stored form, so emitting first left it reading the PREVIOUS save — four cards in, three on the strip, permanently one behind, plausible and wrong by one and invisible unless you compare the strip against the store.
- **`session.js` is the one answer to "what am I holding".** There were EIGHT set-of-cards containers and SEVEN answers to "which card is selected" (`selectedCards[topCardIndex]`, `browseSet.indices[pos]`, `orientation.anchor`, `Discovery.current`, `Force.pinned`, `hovered`, `deckState.commander`) with nothing reconciling them — that is *why* a click meant something different in every mode. Session owns **focus** and the **library**. It deliberately does NOT own the graph's storage: `force.js` holds nodes as live d3 bodies mutated every tick, so a second membership array would recreate the duplicate-model problem — instead force **registers itself as Session's graph provider** (`Session.useGraph`) and everything else asks Session. Still out of scope on purpose: `Build.active` (a loaded decklist) and `Drill.indices` (a re-layout subset) are different concepts, and `browseSet` stays because box-select is a different question. `deckState` is gone entirely with the deck builder.
- **Explore's lens is LIVE, not a snapshot — but arriving is not asking for it.** `orientation` holds only `{label}`; membership comes from `Session.rows()` on **every render** and the anchor from `Session.focus`. A snapshot copied at mode-entry makes the atlas a photograph of your walk — grow the graph and nothing moves — and no styling fixes that. **`setMode('explore')` must not auto-orient**: entering with a lens already applied opens the atlas with 97% of itself at 8% alpha and the camera elsewhere, so the atlas almost never gets to be the atlas and the dimming reads as a rendering fault. Entry clears the lens, the region focus, the legend focus and the selection, then refits; `orientTo` keeps every other caller, so the lens re-engages when you ask for it from inside Explore.
- **One grouping registry, `MM.GROUPINGS`, because a colour is a language.** Four groupings (`supertype`, `role`, `color`, `rarity`), each `{label, keyOf, palette, order, ensure?}`. Before it there were two unrelated taxonomies on the same screen: the map's three palettes here, and `build.js`'s own `FAMILY_COLOR` for role bars — two legends that could never agree. Build now reads the registry (`familyColour()`/`familyPriority()`, **lazy functions, not top-level constants**, so it never touches `MM.*` at module-evaluation time), and its mana curve is **segmented by the current grouping** instead of one flat gold bar. Changing the overlay calls `regroup()`, which repaints the map *and* Build's panel — repainting only the map left the curve answering in supertypes after you had switched to roles. `order` is authoritative everywhere: `Object.values(groups)` is hash order, which made the legend shuffle between renders. `role` carries an `ensure()` that lazy-loads `card_roles.json` (0.39 MB gz) only when selected — never in the 1.83 MB discovery boot.
- **Aura at altitude, crisp up close — the ramp runs the OPPOSITE way to brightness.** Two ramps in `render/canvas.js`: `closeness()` (0 at the fit, 1 by neighbourhood scale) drives point size and alpha, so cards get brighter as you approach; `auraLevel()` is its inverse and drives the additive halo and the radial vignette. Zoomed in, Explore has to converge on Discover and Build — the same force engine, drawing plain dots with **no halo at all** (there is no `shadowBlur` in `force.js`) — and a halo that grew as you approached both broke that parity and sat on top of the points you were reading. Atmosphere belongs where a card is one pixel and only the shape of the cloud is legible. Units: `transform.k` is **relative to `baseFit`**, so k=1 is the whole-map fit; constants in absolute scale leave the ramp flat and on/off then measures pixel-identical. **The halo's cap is measured, because "some aura" and "a wash" are a factor of two apart**: alpha coverage of the canvas at the fitted view against a 4.5% no-halo baseline is 68.4% at cap 0.55 / radius 3.2x (clusters lost inside it), 50.9% at 0.35/2.4x, and 35.9% at the shipped 0.25/1.9x, where each cluster reads as a lit island and the space between stays black. Full-strength ink is 4.2% at every setting — this moves the halo, never the cards.
- **A `discover_page` test that reads `MM.allData` is racing the projection, by design.** The discovery fixture waits on `Discovery.isReady()` and deliberately NOT on `MM.allData` — booting the front door from 0.56 MB *without* the 12.9 MB projection is the property those tests exist to observe, so the fixture cannot wait for it without destroying what it measures. Three tests then read `MM.allData` anyway. It arrives behind the landing, so on an idle machine it is always there and the race is invisible; under `-n 4` it is not, `findIndex` returns -1, and the failure reads **`slug not derived from the commander: untitled`** — a timing bug wearing a schema bug's error message. One failure in three parallel runs found it. `conftest_viz.await_projection(page)` is the fix and names the reason; call it before touching `MM.allData` on a discovery page. This is the sixth of the same family: every one was a wait on the machine instead of on the behaviour.
- **The atlas drifts, and the drift is in the PROJECTION — never in the data.** `render/canvas.js` adds a time term between `wx`/`wy` and the screen: `proj()` applies a differential swirl about the fit's centre plus a bounded Lissajous drift, and `unproj()` is its **exact** inverse, so `pick` keeps landing on the card under the cursor (measured: 5 of 5 named cards hit exactly with a 3px pick radius while the field is moving). Moving the points instead is the one implementation that cannot work here — `buildTree` is 23.5 ms and its signature is deliberately blind to positions, so per-frame mutation either rebuilds the quadtree 20 times a second or reproduces the exact stale-hit-test failure `reindex()` exists to document, and every world-anchored thing (region labels, the search highlight, drill's local layout) detaches with it. Only two callers still use the STATIC mapping, both on purpose: the cached contour field and `setCamera`'s target.
- **It is a sway, not a rotation, and that is a correctness decision.** A galaxy that really rotates *winds up*: shorter inner periods wrap the arms, and cards PaCMAP placed side by side end up a quarter of the map apart — the picture would be lying while still looking good. A rigid rotation avoids the shear and costs spatial memory instead (the region you learned was north ends up west). So the excursion is bounded — peak **32 px on a 900 px viewport**, always returning — with Kepler kept where it is legible: period varies with radius (T ∝ a^1.5, rim slower than core) and phase lags outward, so each instant is a shallow spiral that unwinds and rewinds. `test_the_drift_is_bounded_and_returns` asserts both halves; an accumulating motion passes the "does it move" test and fails that one.
- **Motion rides the aura's altitude ramp, and stops for everything precise.** `ambient()` is 1 at the fit and 0 by the time a region fills the screen (`K1: 6`, same as `AURA_K1`), so points slide home as you approach and Explore still converges on Discover and Build up close. It also stands down when the tab is hidden, when `prefers-reduced-motion` is set (the boot default; the Motion button reports the renderer rather than the markup), and when the canvas is off screen — that last check must read **`canvas.offsetParent`, not `host.offsetParent`**: `#plot` is shared with the force graph and stays visible in Discover and Build, so asking the host animated 34,890 points into a surface nobody could see. Per-point trig is avoided entirely by tabulating (cos, sin) into 96 radial bins once a frame; the sway is a function of radius alone, which is also *why* the inverse is exact.
- **The halo saturates whole-map ink measurements, so measure zoomed in.** `test_canvas_draws_density_contours` asserts topo triples the ink; at the fit the halo already covers ~36% of the canvas and contours draw over the same clusters, so the toggle moved total ink by 2.8 points and the ratio test died — not because contours stopped drawing but because the *measure* had saturated. Zoomed in, where `auraLevel()` is 0 by design, the same toggle is 7.6x. When an atmospheric effect and the thing you are measuring occupy the same pixels, move the camera rather than weakening the assertion.
- **Label outlines are written inline, scaled to each label's own opacity.** Region names sit at cluster centroids — i.e. on top of the densest colour — so they need a ring, not a drop shadow. But the ring is per-label: a fixed 0.95-alpha ring under a 0.28-alpha context label is more opaque than the text and renders as a dark smudge. CSS cannot see the opacity, so `setAnnotations` emits the `text-shadow`. Related: `refreshCanvasLabels` drops anything under **0.09 alpha** rather than 0 — placement is greedy and sorted big-first, so a country name fading through 0.03 still claimed the largest collision box on screen and suppressed the readable neighbourhood name under it.
- **Colour-by defaults to supertype, and the palette is frequency-aware.** Creature is **55.1%** of the corpus (19,240 of 34,890), Planeswalker 1.0% (338) and Battle 0.1% (39) — so saturation runs *inverse* to frequency: muted bone for creatures, hot accents for the rare types, material tones for the permanents and a blue→violet→rose sweep for the spell types. The old palette gave Creature `#22C55E`, the same green `COLOR_PALETTE` uses for G, on more than half the points — the supertype map looked like a broken colour-identity map. Legend rows are **controls**: clicking one spotlights that group, and it composes with a focused region through one `spotlightFor(g)` predicate rather than a second dimming path — a group focus is one scalar per trace and never touches the 34K array.
- **Two boot literals, one bug, found a month apart.** `fetch(MAP_CONFIGS.default.projection)` and `loadRegionData('default')` both hardcoded the boot map, so changing the default left `currentMap` saying one thing while the coordinates — and then the region names — came from the other. Neither errors: the projection silently draws the wrong positions and the label pass silently finds no data and emits an empty list. Both now read `currentMap`, and both selects are pinned from the JS defaults at boot rather than from markup order.
- **`stage.js` owns the surface; it never stores a coordinate.** The two canvas renderers (`render/canvas.js` for the 34K atlas, `force.js` for the graph) shared *zero* lines while separately implementing canvas+DPR resize, d3-zoom, the draw prologue, world↔screen, fit-to-extent and greedy AABB label collision. Stage holds all of it. The reason it does not own positions: force mutates node x/y every tick, the atlas never mutates points and moves only the transform — an abstraction owning both would be a union of two designs. Label placement is **incremental** (`Stage.placer`) because the graph draws each label on accept and caps on the number *accepted*, sharing one collision set between edge and node labels; `placeLabels` is a batch wrapper for the atlas.
- **`mode:'edges'` ≠ `mode:'lines'`.** A `lines` layer is one flattened polyline, one colour, excluded from the quadtree — fine for Build's verified lines, useless for "this edge is a synergy, that one an obsolescence". `edges` carries `[{source:[x,y], target:[x,y], rel, reason, d}]` and inks via `Stage.INK`, so an edge means the same thing on the map as on the graph. Coordinates are explicit, not row ids — the renderer knows nothing about cards. Edge layers are excluded from the quadtree AND the legend. Test it by **reading pixels**; "the layer is present" passes while nothing draws.
- **One surface per mode, and the CSS must name the RIGHT one.** `#plot.force-mode` hid `.js-plotly-plot`/`.plot-container`/`.svg-container` — Plotly elements that stopped existing when Plotly was deleted — so in the graph modes the 34K atlas kept drawing underneath with its labels and legend. It survived a mode-by-mode check because `.map-canvas` is created lazily on the first Explore render: boot straight into Discover and there is nothing to leak. **Test the ordering that exposes a leak (Explore first), not the one that hides it.**
- **`clearSelection` clears the selection; `escapeOnce` peels.** They were one function, and every plain click runs "replace the selection" first — so clicking a point while a region was focused ran the Escape chain, cleared the focus and refit the camera. The `orientation` branch had done the same thing for longer and less visibly. Only the Escape key may peel (region → orientation lens → selection); `MM.closeDetail` is the plain clear.
- **A cluster-label click ZOOMS; it does not drill.** `focusRegion(id)` frames the region from its members' real extent and filters the map to them — same points, same coordinates, closer camera, so picking keeps working. Drill is a different operation (re-embeds the subset via stress majorization) and stays on the toolbar and box-select, where a re-layout is an explicit request. Escape peels outermost-first: region → orientation lens → selection.
- **`updateLayerBy` moves points without telling the quadtree.** The tree signature is layer lengths + endpoint ids — cheap on purpose (a rebuild is 23.5 ms and `setLayers` runs per keystroke) and therefore blind to positions. Drill mutates coordinates for 90 frames with the signature unchanged, so hit-tests kept landing on pre-drill positions: "the points settle and then I can't interact with them". Call `mapRenderer.reindex()` once after any in-place position change — at settle, never per frame.
- **One visibility predicate.** `render()`'s group loop re-tested `activeSupertypes` against `allData` while `filtered` (used by contours and the status count) applied its own — two places deciding what is drawn, silently disagreeing, so a new filter added to `filtered` changed nothing on screen. They now share one `visible(d, i)`.
- **Two coordinate systems**: drill mode re-lays-out a subset from the embeddings, so a drilled position is **local** and is not the world map's. Anything anchored to world coords (region labels, search highlight, selection ring) must be suppressed or re-anchored via `Drill.localPosition()` while drilling. See `docs/viz.md`.
- Paths in `config.py` are `__file__`-anchored (CWD-independent); override with `MANAMAP_DATA_DIR` / `MANAMAP_VIZ_DIR`.
- **Two embedding spaces, two different jobs.** `embeddings.npy` is the **layout** space (colour/type) and feeds `projection_2d.json` *only* — its near-zero triplet loss is fine for a task whose whole content is "same colour, same type". `embeddings_ability.npy` is the **function** space and is the sole source of similarity: Find Similar, the walk and drill all read it regardless of which map is displayed (`SIMILARITY_EMBEDDINGS` in `viz/js/mana-map.js`). Similarity must never follow the displayed map: the layout space knows only colour and type, so asking it for neighbours returns arbitrary same-colour cards.
- **The function model was rebuilt after measuring a collapse**: it had been using 5.97 of its 128 dimensions and losing to the frozen MiniLM text it was built from. Now 27.87 effective dims, recall@10 0.093 → 0.245, median rank 995 → 78. Three changes: in-batch InfoNCE instead of a triplet margin (a margin stops teaching once satisfied), positives from `card_roles.json` rarest-role-first (the old ≥2-shared-tags rule fell back to random for most of the corpus, and `ROLE_BODY_FALLBACK` is excluded because it labels every creature), and a fixed-weight text passthrough making similarity exactly `0.7·cos_learned + 0.3·cos_text` so the model **cannot** discard the text as it did before.
- **A COMMA CANNOT SEPARATE CARD NAMES — 3,222 of 34,890 contain one (9.2%), and they are the legendaries you would seed a walk with.** Discover accepts cards you name (a textarea, or `?cards=`), and the pilot's own two forms are `Zur the Enchanter` and `1) zur, 2) sol ring`. Splitting on commas turns the commonest input into two cards that do not exist and fails **silently**. So the ENUMERATION separates: a `1)` / `2.` / `3:` marker splits only where an item can BEGIN — start of text, after a newline, or after a comma — which is what makes `1) Miirym, Sentinel Wyrm, 2) Sol Ring` two cards and `Miirym, Sentinel Wyrm` one. Requiring a boundary also protects the **eight corpus names carrying a marker inside them** (`Vault 87: Forced Evolution` and five Fallout siblings), which a naive `\d+[).:]` halves. The normalised text then goes to **`Decklist.parse`, never a second name reader** — it is fixture-locked to the Python parser and already handles quantity prefixes and `*CMDR*`. Unresolved names are REPORTED: a typo that quietly yields a one-card walk is indistinguishable from the feature not working.
- **`Discovery.seedFromRows(rows, label, opts)` is the one seed path, and it exists because the fifth hand-written caller would break the rule again: GROWING MUST NEVER BE ABLE TO DELETE.** `Force.enter([row])` REBUILDS; two callers shipped that bug, each destroying a walk silently. So there are **two buttons, each saying which it is** — *Start here* reseeds (the explicit request that legitimises replacement), *Add to walk* adopts and appears only once there is a walk. `Force.adopt` is exported for it: `branchByRow` was the only way in and also pulls the row's relations, right for a relation click and wrong for "add this card", where the graph grows by twelve when one was asked for. Three of four seed sites route through the helper; **Build deliberately does not**, because `seedFromRows` ends by calling Discovery's `render()`, which would repaint Build's roles and curve with Discover's landing controls — the defect `Force.renderPanel` was taught to avoid by asking `MM.mode`.
- **An open verified line explains itself, from prose that was already on the wire.** `buildEdges` kept a stack's `title` and dropped the document it came from, while `loadDeck` was already fetching that whole document. Three sources keep their own slots and attribution rather than being blended: the authored `manual_prose.combo_lines[<id>]` (47 of 50), `resolution.answer` (4 of 50 — which is why it cannot be primary), and `resolution.final_state.summary` (**50 of 50**, the floor). Measured fleet-wide before shipping: **zero published lines have no prose**. Nothing is derived or truncated — a checker read those words, and re-wording them puts a ✓ over prose no checker saw; the test was proven by truncating a summary to 120 chars. Only the OPEN line renders (median 838 chars, max 4,337). **The bottom fade is a claim that must hold in both directions**: it comes off at the end AND for a block shorter than the cap, which never fires a scroll event — goblin-storm 002 is 877 characters, and a fade over a complete text is a lie about there being more.
- **A verified line is a CLIQUE, and a clique has no arrows — `engine.json` is the only artifact that knows direction.** `{source, target}` is whichever order the pair was built in and `findLink` matches either way, so an arrowhead there would be array order wearing a claim. Build orients a pair only when it SPANS the engine line's two stages (`from` → `to`); a pair sitting wholly inside one stage gets none. On ur-dragon that is **5 directed edges of 196** — the arrow is the exception, and earned. **A stack can carry two lines**: ur-dragon's 002 is cited for `bodies` and for `triggers`, and `.find()` would silently drop half of what that board proves; all matching lines are read, agreeing nouns joined (`bodies · triggers`), and two lines DISAGREEING on direction draw no arrowhead at all. Deliberately NOT done: parsing magnitudes out of resolution prose — that is the string-matching this repo keeps rejecting, and a magnitude belongs as an authored field on the engine line.
- **A curve bar and a role row are CONTROLS, and the click had to route by view.** The colours already agreed (`renderManaCurve`, the role bars and the map scatter all read `MM.GROUPINGS`); only interaction was missing. Routed exactly like `applyLine` and for the same reason: **Build defaults to the GRAPH**, so a handler that only moved the map spends its time restyling a `display:none` canvas, which reads as the click doing nothing. A group and a line are two answers to "show me", so taking one puts the other down. **The bug it exposed**: node fill was dimmed and then `globalAlpha` reset to 1 before the rim was stroked, so a spotlight left 96 bright outlines and the picture never dimmed — `Force.setLine` had shipped with the same defect.
- **The workbench is the landing page, and its games chip had never rendered once.** `workbench.js` read `info.status.games`; `deck-info` writes the games under **`info.record`** and uses `info.status` for stage counts. Two decks with logged games looked identical to nine without — it survived because a *missing* chip is invisible while a *wrong* one would have been reported in a day. Also: **`info.next` is a sentence, not a cell.** As a table column it broke the layout, since every other column is `nowrap` and their widths summed past 100%; it gets its own full-width row. And the whole-card link is gone in favour of three labelled ones (MANUAL · DOSSIER · ON THE MAP) — a card that opens two different things depending on where you click is the interaction bug already fixed in the atlas.
- **`combo_graph.json` was registered in `MM.DATA` and fetched by NOTHING.** The deck builder that read it is deleted. A registered URL nobody requests reads as a live dependency, so the 4.5 MB artifact behind it looked load-bearing to anyone deciding what could go. The registration is gone; the FILE stays, because `config.py` uses it as the invalidation proxy for `combo_details.json`, which several Python consumers do read. **MEASURED AND NOT KEPT**: Spellbook carries a `description` on every one of its 83,261 variants (median 405 chars), and writing it into `combo_details.json` costs **+36.4 MB on a 25.7 MB tracked file** with no LFS. As an id-keyed gzipped sidecar it is 4.4 MB — affordable, but it has no reader: the browser's prose comes from the per-deck stacks. The consumer that would justify it is `engine_facts`, which hands `deck-engineer` contained combos with no account of how they work. Key it by Spellbook `id`, never by position.
- **Two decklist parsers, one contract, enforced by test.** `pilot/fetch_deck.py:parse_decklist` (CLI) and `viz/js/decklist.js` (browser paste-import) are checked against the same **hand-authored** fixtures in `tests/fixtures/decklists/` — hand-authored because generating them from Python would make Python the oracle and both sides would agree with its bugs. The contract is a **projection** onto `{name, quantity, is_commander}`: Python also resolves printings and foils, the viz strips-and-discards them, and that is where the one real hazard lives (`_PRINTING_RE` is `$`-anchored, so `*F*`/`*CMDR*` must come off *first*). Imports resolve against `viz_index.json`, never `data/decks/index.json` — Build's deck picker refuses unknown slugs and an imported deck has none.
- **`d3.drag` swallows clicks by default.** `clickDistance` is 0, so one pixel of movement between mousedown and mouseup suppresses the `click` event entirely — measured here: 0px delivered, 1px and 3px swallowed. Any canvas that has both a drag and a click handler needs an explicit tap tolerance (`force.js` uses 6) or interactions will feel intermittently dead in a way that looks like latency and isn't.
- **Discovery is the front door; `?mode=explore` gets the atlas.** The landing is one random card (`viz/js/discovery.js`), not the full-corpus scatter. It is **the same force engine Build seeds** — one simulation, because a second would be the duplicate-k-NN mistake this repo has undone twice. Discovery reaches a first branch on **1.83 MB gz** (viz_index 0.56 + neighbours 1.27), though 4.80 MB crosses the wire in total, since the projection (2.90) and region labels (0.06) are fetched unconditionally behind the landing, and **branching is synchronous**: nothing in discovery reads the embeddings, so they are never fetched on that path. A *seeded* walk (deck/region) still awaits them — `linkWithinFromTable` only links cards whose top-12 are also in the set, which on a 97-card deck is 38 links instead of ~290.
- **Anything called during mana-map.js's boot runs INSIDE the IIFE, before `window.MM` exists.** Touching `MM.*` there throws, which aborts the IIFE, so `MM` is never exported and every later module fails at its own top level too — one ordering mistake, four broken files. Discovery takes its URLs by injection (`Discovery.configure`) and the boot mode is applied in a `queueMicrotask` for exactly this reason.
- **One relation mechanism: `MM.relate(row, rel)`, and it always grows the graph.** The controls render inside `buildCardDetailHtml`, so every panel that shows a card has them — including the **Keep** button, since keeping a card you found in the atlas is the same act as keeping one you walked to. From Explore, `relate` switches to Discover seeded on that card: Explore is a **launchpad**, not a second mode with its own answer to the same button. **One control must mean one thing** — a relation button that branched in some modes and opened a browse set in others is why the atlas felt dead next to the walk. Box-select still opens a browse set; that is a different question, asked a different way. If you add a panel that renders card detail, pass the **row**, not just the record: a relation needs the row id, and a panel that has only the record is a silent no-op.
- **Growing must never be able to delete — seed only when there is nothing to lose.** `Force.enter` picks up where you left off *only when handed no seed* (`force.js:555`); pass an explicit `[row]` and it takes the rebuild path and replaces the graph with that one card. Two callers got this wrong and each destroyed a walk silently: `MM.relate` routed every not-yet-present card through `Discovery.show` (which calls `newWalk(true)`), and `Discovery.enter` reseeded with `[current]`, so **merely looking at the atlas and coming back** wiped the graph. The rule now: reseed only when `Force.nodeCount === 0`, otherwise `Force.branchByRow` **adopts** the row — `adoptRow` places it at the graph's centre of mass (its world position is usually off screen) and links it to what it already belongs beside. Fixing only `relate` did not hold, because the outer `Discovery.enter` path destroyed it first — check both when touching mode entry.
- **`neighbours.bin` is pre-sorted and must never be re-sorted client-side.** It carries 12 similar + 10 synergy + 5 obsoleted-by row ids per card so the browser can branch *synchronously* — no await mid-gesture, and without the 16.8 MB embedding matrix (2.4 MB gzipped for the whole discovery boot, against 18.4 MB before). Its similarities are uint8-quantised **for edge length only**; ordering is the array order. Re-sorting by a lossy value changes the top-10 for ~two thirds of cards, because the space is a narrow cone (median pairwise cosine 0.714) — it would read as a model regression rather than a precision bug. The header carries a sha256 of the embeddings it was built from and `tests/test_viz_index.py` fails if they diverge, because a stale table parses fine and answers confidently.
- **`manamap eval-embeddings` (step 15) is how you know.** It scores every embedding artifact against `data/eval/similarity_golden.json` — hand-authored, and it must **stay** hand-authored: training mines positives from tags/roles, so an eval derived from those would only measure whether training memorised its own supervision. Quote the **test** split; `dev` was used while diagnosing. **Do not tune hyperparameters on it** — sweeping the text weight looked like a win (0.258 recall@10) until selecting on `dev` picked a different value and the splits disagreed; at ~50 dev / ~160 test queries those differences are noise. `tests/test_embedding_quality.py` holds regression floors plus one still-failing `xfail(strict=True)` gate (neighbour spread 0.0315 vs a 0.05 target) whose threshold was deliberately not lowered to match the result.
